# Project Maintenance Rules

- Preserve existing novels, model bindings, Skills, run history, and formal manuscripts during migrations.
- Do not call paid model APIs from automated tests or maintenance checks.
- Any behavior change to workflows, model routing, token budgets, StoryState, quality gates, recovery, or project files must update `README.md` or `docs/maintenance.md` in the same commit.
- Schema or state changes must update the applicable design document under `docs/superpowers/specs` and include an idempotent migration test.
- User-visible run events must distinguish model failure, Runtime rejection, quality failure, fallback, and successful commit.
- Run the focused regression test first, then the complete test suite before restarting the console.
- Never restart while a run is `queued`, `running`, or `cancelling` unless the user explicitly authorizes termination.

## Virtual Development Council

- Use the project-local `novel-dev-council` Skill for every non-trivial feature, behavior change, bug fix, refactor, workflow change, or regression-risk task in this repository.
- Team review is opt-in only. Do not launch product, novel-business, technical, test, or other review subagents unless the user explicitly requests **团队评审** for the current task. A prior request does not carry forward. Without that exact authorization, work as one agent and use the Skill only for scope, regression, rollback, and verification gates.
- The lead agent is the only default file writer. Review-role subagents MUST NOT edit the shared worktree unless the lead explicitly assigns non-overlapping implementation files after accepting the change contract.
- The council governs repository development only. Never inject it into story-writing prompts, register its roles as provider/model bindings, or treat it as an application Runtime Skill.
- Council review never broadens user authorization. Explanation and evaluation remain read-only; implementation, destructive actions, paid calls, restart, termination, and formal-data changes require matching user authority.
- Before completion, enforce the Skill's task-local baseline, unchanged-behavior contract, focused regression, next-authoritative-boundary proof, related tests, complete-suite requirement, single-agent clean-room final-diff review, and no-new-hard-issue gate. Use an independent reviewer only when the user explicitly requests **团队评审**.

## Production Incident Memory Gate

- Every terminal production failure must enter the shared incident mechanism with a stable incident key, root-cause family, occurrence count, first/last-seen timestamps, and an implementable known resolution. Normalize volatile run IDs, file paths, entity names, segment numbers, and counts without collapsing materially different failures.
- Reclassify legacy terminal events that lack incident metadata when they are read, so old failures remain part of the incident history without a destructive migration. A recurrence must emit a visible **已识别为历史同类问题** event before the terminal failure.
- Add every newly observed production failure to the incident catalog and a production-shaped regression fixture. Containment, rollback, or a new validation error is not resolution; the catalog entry must name the retained authority, smallest repair scope, retry/fallback behavior, and next authoritative boundary that proves recovery.
- Before changing a workflow, search the incident catalog and applicable regression fixtures for the same family. A fix is incomplete if it reintroduces any previously registered hard incident in initialization, planning, causal-chain generation, execution manifests, drafting, split/merge, polish, targeted/manual revision, AI issue refresh, final review, or publication.
- Every production fix MUST perform a forward-risk scan across all later workflow stages and every structurally similar call site, using the complete historical incident catalog rather than only the current error string. Map the underlying failure mechanism (for example context/input capacity, output truncation, transport interruption, parser ambiguity, ownership granularity, stale authority, partial checkpoint, merge conflict, or semantic regression) to planning, causal-chain, manifest, drafting, merge, polish, targeted/manual revision, AI issue refresh, final review, and formal promotion. Either repair and test each reachable sibling path or record concrete code evidence explaining why that path is not susceptible.
- A green unit test built from an idealized fake model is not sufficient when production behavior can differ through provider context metadata, duplicated system/user envelopes, unknown output ceilings, thinking-token consumption, normal-finish incomplete output, fallback-route capacity, network termination, cancellation, resume, or conflicting checkpoints. The regression ladder MUST include the original production-shaped authority and payload proportions, the applicable provider-capability uncertainty, and successful continuation through the next authoritative boundary; separately authorized real-provider validation is performed only after these offline gates pass.
- Completion reports MUST state which historical incident families were checked, why the previous tests missed the production failure, what sibling risks were found, and which tests prove they cannot migrate into later stages. If that forward-risk evidence is incomplete, report the fix as contained or unresolved rather than complete.

## Non-Deterministic Model Output Gate

- Model-generated prose and receipts are open-ended outputs. Never treat one canned article, one exact sentence, one fixed issue list, or one ideal fake-provider response as representative production coverage. Except for authoritative quoted input, tests MUST assert stable semantic and protocol invariants rather than exact creative wording.
- Every changed model-output boundary MUST cover at least six materially different valid realizations, at least two malformed/incomplete/contradictory realizations, and at least two capacity or transport faults. Include the applicable duplicated, reordered, wrapped, verbose, terse, multilingual, output-limited, and interrupted provider-envelope variants. The variants must exercise different surface wording and structure while preserving the same authority contract. If a change does not touch model output, its forward-risk report must provide concrete code evidence for that exemption.
- Stable test oracles include authority hashes, ordered ownership, event and atomic-beat coverage, actor-action-result binding, causality, viewpoint, timeline, knowledge state, entry/exit state, issue identity, exact evidence occurrence, no duplicate ownership, atomic promotion, and successful continuation through the next authoritative boundary. Creative wording, dialogue, description, rhythm, and non-dependent micro-order remain open unless explicitly locked by user authority.
- Prefer deterministic parameterized, metamorphic, mutation, property-based, and pairwise-combination tests with recorded seeds and shrinkable failure fixtures. Live randomness may supplement but never replace reproducible cases. Any random failure must be reduced into a stable production-shaped fixture before the fix is considered complete.
- A test that replaces `_stage` with a perfect response or invokes a splitter directly cannot by itself prove production recovery. At least one local integration test for each affected route MUST retain the real stage assembly, capacity policy, role binding, primary/fallback routing, provider envelope, checkpoint path, and validator while replacing only the paid network boundary with a deterministic fake gateway.
- Completion evidence MUST distinguish deterministic invariants from open creative expression and list the tested output variants. If only one generated realization was exercised, report the change as insufficiently verified rather than complete.

## Open-World Requirement Non-Narrowing Gate

- Treat user terms such as **all**, **future**, **similar**, **common**, **root cause**, **different models**, **different providers**, **different genres**, or their Chinese equivalents as an open-world requirement. MUST NOT silently narrow that scope to the currently observed payload, field names, provider, novel, error string, or fixture. If the requested scope cannot be met, report `contained` or `unresolved` and obtain an explicit user decision before narrowing it.
- Record every material user MUST as a traceable contract before implementation: original requirement, operational definition, forbidden narrowing, implementation boundary, invariant-based test paths, and completion evidence. A missing mapping is an incomplete change contract. User-authorized systemic compatibility and automatic recovery take priority over the preference for a smaller patch; “smallest coherent patch” MUST NOT justify a sample-specific workaround.
- A recurring incident family, or an explicit request for common/root/systemic resolution, MUST be solved at the shared mechanism boundary. Adding an observed error string, provider name, schema key, label alias, or one more `if/elif` branch is not a systemic solution unless a closed-world proof shows the representation set is finite. Observed aliases may exist only as adapters above a canonical invariant-driven representation.
- For a changed model-output boundary, the six valid realizations MUST span at least four materially different topology classes, not merely whitespace, wrapping, wording, label aliases, or key order. At least two valid cases MUST use container names or wrapper arrangements absent from both the implementation and all production fixtures. Tests MUST also cover ambiguous multiple candidates, duplicate or reordered ownership, and an unknown machine-control field that triggers canonical retry rather than unsafe guessing.
- Classify completion as `contained`, `case_fixed`, `systemically_resolved`, or `unresolved`. `contained` means damage was prevented but the requested path still stops; `case_fixed` means only the declared closed-world case recovers; `systemically_resolved` requires production-shaped recovery, unseen valid variants without code changes, ambiguity safety, and successful continuation through the next authoritative boundary. Only `systemically_resolved` may be described as a root or common fix for an open-world requirement.
- Every forward-risk report MUST state the scope classification, forbidden narrowing, resolution status, topology classes, unseen valid variants, unknown-variant behavior, and requirement-to-code/test/evidence traceability. The strict gate MUST reject an open-world report that claims only containment or case repair, or whose variants do not demonstrate structural diversity.
- When a new production payload recurs in an incident family previously marked resolved, immediately downgrade that family to unresolved until the existing implementation handles the new payload without a sample-specific branch and the production fixture crosses the next authoritative boundary. Incrementing an occurrence count or recognizing the family is not resolution.

## Root-Cause Architecture Convergence Gate

- A repeated incident family or a user request for a root, common, permanent, or future-proof solution MUST begin with a mechanism-level root-cause analysis and an architecture-convergence plan before implementation. Map every parallel parser, validator, state transition, retry path, checkpoint, and authority boundary that shares the mechanism; fixing only the call site that exposed the latest payload is forbidden narrowing.
- Accumulating provider-specific parser aliases, regular expressions, or compatibility branches MUST NOT be described or accepted as a root solution. Presentation tolerance must converge at one versioned conversion boundary using a mature structural-alignment or schema technique, followed by authoritative domain validation, typed bounded recovery, and downstream continuation tests. A new compatibility rule is allowed only as a documented temporary bridge with a removal gate.
- Evaluate applicable mature standards, maintained libraries, or established architecture patterns before designing custom machinery. Relevant examples include grammar- or AST-based parsing, typed intermediate representations and schema validation, explicit state machines or Saga-style recovery, idempotent checkpoints, capability negotiation, and property-based or metamorphic testing. Record the selected pattern, fitness evidence, rejected alternatives, and operational tradeoffs. Popularity alone is not evidence, and this rule does not justify importing a framework that would create a competing authority or workflow.
- Patch accumulation is prohibited as the primary systemic solution. An observed regex, error string, provider name, model name, schema key, label alias, or additional `if/elif` branch MAY exist only as a bounded adapter above one canonical invariant-driven boundary, or as explicitly classified temporary containment when no safe systemic recovery is yet available. Temporary containment MUST name its owner, expiry/removal condition, rollback, regression fixture, and follow-up architecture path, and MUST NOT be reported as root resolution.
- Every systemic refactor MUST define a convergence budget: inventory the duplicated or competing paths before the change, identify the single target boundary, and provide a staged delegation, deprecation, or deletion plan for legacy paths. Adding a new abstraction while leaving all old implementations authoritative is incomplete unless a time-bounded dual-read migration and equivalence gate require it.
- A custom implementation is acceptable only when the change contract explains why available mature techniques or maintained dependencies do not fit the repository's authority, compatibility, security, licensing, performance, or rollback requirements. External adoption likewise requires maintenance health, license, security boundary, data ownership, migration, and rollback review; "market-proven" is not permission to outsource StoryState or formal-write authority.
- Completion evidence MUST demonstrate mechanism-level simplification as well as recovery: production-shaped reproduction, unseen structurally different valid variants, ambiguity safety, successful continuation through the next authoritative boundary, and proof that structurally similar sibling paths no longer depend on stacked special cases. If duplicate paths remain authoritative or only the observed case recovers, classify the result as `contained`, `case_fixed`, or `unresolved`, never `systemically_resolved`.

## Versioned Contract Adapter Gate

- Any newly accepted representation of model-generated structured data MUST be implemented through `novel_flywheel.generated_artifacts.CONTRACT_ADAPTER_REGISTRY`. Inline compatibility acceptance inside `workflows.py`, provider clients, validators, or retry loops is forbidden. Workflow code may invoke the registry and authoritative validators, but may not own representation-specific conversion branches.
- Every adapter MUST declare a stable name, version, source topology classes, canonical topology, proof obligation, and provider/narrative independence. It MUST emit a content-addressed audit containing only hashes, topology, version, and transformation codes; never raw story text, prompts, credentials, provider-specific wording, or project identifiers.
- A conversion is permitted only when Pydantic plus deterministic proof establishes semantic equivalence. Partial sets, duplicate identities, unknown machine controls, conflicting candidates, truncation, or any representation requiring narrative inference MUST remain unconverted and enter the typed local-repair / receipt-only retry / configured-fallback ladder.
- The adapter registry is an architecture budget, not an alias collection. Adding an adapter requires a closed-world proof for the representation class, unseen structural variants, malformed and ambiguous counterexamples, idempotence, cross-genre preservation, downstream-boundary continuation, and an explicit review of whether an existing adapter can be generalized or deleted instead. Provider names, model names, genre names, production entity IDs, observed prose, and error-message literals are prohibited from adapter descriptors and decisions.
- Protocol-repair budgets are independent from semantic-repair budgets. Repeating an immutable receipt on one route is bounded; exhaustion MUST use the configured independent fallback route when available and re-enter the same canonical and domain validators. A protocol defect introduced after semantic progress MUST NOT become terminal merely because the semantic mutation budget was consumed.
- A protocol recovery schedule MUST own route selection end to end. Its primary attempts may not call a gateway method that performs a hidden fallback, and route-execution exceptions MUST be converted at one shared boundary into typed, hash-only reliability failures before the schedule decides whether to retry or select the configured fallback. Provider names, domains, status-specific branches, and raw transport errors MUST NOT enter route policy or story prompts.
- Do not require a model to duplicate Runtime-verifiable authority across descriptive fields. Evidence IDs, exact extractive spans, hashes, ranges, and identities MUST be bound and proved by Runtime once; a missing paraphrased or repeated echo in `reason`, labels, or summaries is not an independent semantic defect. Remove redundant echo coupling at the shared contract boundary instead of adding per-call repair branches, while keeping non-empty descriptive fields and all downstream semantic validators mandatory.

## Generated-Output Parsing Compatibility Gate

- Every new or changed parser for model-generated, imported, or user-authored semi-structured text MUST normalize presentation variants at one shared boundary before semantic validation. Cover CRLF/LF, surrounding whitespace, common Markdown or HTML wrappers, fenced/unfenced blocks, full-width punctuation or digits, and documented label aliases when applicable.
- Normalize identifiers and labels with Unicode-aware comparison (including NFKC when safe), but never rewrite free-form prose merely to make parsing easier.
- Preserve every previously accepted representation unless an explicit migration and rollback path is documented. Formatting differences alone must not become semantic hard failures.
- Separate deterministic syntax normalization from semantic validation. Repair harmless wrappers locally; reserve blocking errors for malformed data, multiple JSON-object payloads, canon conflicts, or narrative contradictions. Never silently choose the first or last payload when more than one valid candidate exists.
- New JSON-object parsers MUST reuse `novel_flywheel.model_output.parse_json_object`; a custom parser is allowed only for a documented schema-specific repair and must still reject multiple valid payloads.
- Markdown semantic scanners MUST ignore ordinary HTML comments, fenced examples, and templates unless a parser-owned sentinel explicitly claims the block. Extract owned protocol blocks before sanitizing the remaining visible Markdown.
- A parser change is incomplete without table-driven tests for the canonical form, at least two realistic variants, malformed and ambiguous input that fail closed, and a regression fixture or minimal reproduction for any production failure that prompted the change.
- Update `docs/maintenance.md` whenever this compatibility contract gains a new accepted representation or changes failure behavior.

## Generated Semantic Metadata Authority Gate

- Every generated field MUST be classified before validation as descriptive metadata, a machine-control field, or a narrative invariant. A free-form category, label, dimension, reason, evidence kind, or diagnostic phrase is descriptive metadata and MUST NOT gain blocking authority merely because it resembles an enum.
- Preserve descriptive metadata losslessly as raw values. When useful, also store recognized canonical values and unrecognized values separately. Unknown Unicode, Chinese, English, genre-specific, or provider-specific descriptions MUST remain auditable and MUST NOT trigger plan, draft, polish, or revision regeneration.
- Runtime derives authorization and severity from stable authority: hashes, ordered IDs, exact Runtime-owned evidence, deterministic coverage, and explicit narrative invariants. Model classifications and descriptive labels are diagnostic suggestions only. If descriptions contradict complete invariant verdicts, retry or adjudicate only the immutable receipt; do not mutate prose or consume semantic-repair budget.
- Machine-control fields such as patch operations, repair kinds, review decisions, and deterministic check kinds remain closed for safety. Normalize documented aliases at one boundary, preserve the raw control label when it differs, and retry only the machine contract when an unknown or malformed control remains. Never guess an unsafe operation from free prose and never turn a control-protocol defect into a narrative rewrite.
- Parser regression coverage MUST include arbitrary unknown Unicode descriptions, known aliases in at least two languages where applicable, a descriptor/invariant contradiction, a real production-shaped failure, normalization idempotence, and successful continuation through the next authoritative boundary.

## Story-Wide Narrative Integrity Gate

- Every workflow, retry, fallback, resume, parser repair, and context-compaction change MUST preserve story-wide causality, character and knowledge state, timeline order, relationship progression, setup/payoff coverage, and the confirmed ending. Passing a local format check is never sufficient when the change can affect downstream narrative logic.
- Treat every validated artifact used by a downstream writing stage as required authority, including the confirmed outline, event ownership, causal chain, StoryState facts, segment entry/exit state, and applicable promises or ending constraints. If any required artifact is missing, truncated, ambiguous, stale, or semantically invalid, checkpoint the valid upstream work and stop before downstream generation; never continue with a degraded or partial substitute.
- A split model call or resumed task MUST receive the same applicable narrative authority as the original flow. Segment drafting additionally requires the validated owned plan, the previous accepted ending state, and the current handoff. Retries may regenerate only the failed artifact, but must revalidate its hashes, event coverage, ordering, and cross-artifact consistency before continuing.
- A model response with an output-limit finish reason is a truncation risk, not automatic proof of failure or success. It may become validated authority only when an independent artifact-specific completeness check proves schema closure, required event coverage, order, handoffs, and applicable narrative constraints. Otherwise retry the same route with more headroom, then split by semantic ownership; discard incomplete protocol tails and never infer missing narrative facts locally.
- Degraded continuation is allowed only for explicitly advisory material that cannot affect narrative truth or downstream validation. Causal chains, continuity state, event assignments, canon, timelines, promises, and ending constraints are never advisory.
- Regression coverage for a workflow change MUST include truncation at each new model-output boundary and prove that no partial authority is committed, valid upstream checkpoints remain reusable, and downstream drafting does not start until story-wide validation passes.
- Mandatory narrative authority is lossless. Formal outlines, causal chains, locked/confirmed facts, hard-rule sections, execution manifests, and boundary states MUST NOT be sliced by fixed character limits. Context pressure may split semantic work, but it may not omit authority.
- Every prose mutation after draft acceptance, including ordinary polish, structural revision, targeted repair, fallback output, and resumed best candidates, MUST revalidate the exact atomic beats, actor/action identity, viewpoint, location/time/knowledge state, scene order, entry/exit state, and whole-story causality before promotion. On failure, preserve the last accepted complete scope.
- Semantic drift is repaired through a bounded three-level ladder: first regenerate the smallest authorized patch from the exact failure receipt, then rewrite only the affected complete formal segment when a local patch cannot preserve its boundaries, and finally restore the last accepted complete segment or modification group after two failed repairs. Never splice an unvalidated partial repair into accepted prose, silently expand a user-selected revision to unrelated issues, or mark a reverted issue resolved.
- A semantic repair is not complete when it only satisfies event ownership. The repaired scope must retain useful voice, dialogue, detail, pacing, and reasonable length, pass local prose and quality gates, revalidate adjacent handoffs, and pass whole-story adjudication before promotion. A later polish pass may improve expression but MUST NOT reopen an already repaired semantic invariant.
- A full or partial resume MUST copy or deterministically reconstruct every hash-bound artifact needed downstream: causal chain, ready execution manifest and receipt, segment assignments, narrative integrity, and exact accepted prose. A later corrupt segment invalidates only itself and its suffix; it MUST NOT discard an earlier validated prefix.

## Generated Subtask Integrity Gate

- Every generated split, retry, continuation, compaction, fallback, or resumed subtask MUST be rendered from immutable narrative authority plus a fresh current-task contract. A provider call may contain only one executable numeric target and one current event scope; never append child instructions to a rendered parent prompt that still contains the parent target or ownership range.
- Each contract MUST bind the authority hash, task and parent IDs, depth, current target, exact ordered event IDs, entry state, required exit state, and the preceding accepted sibling hash when applicable. A single indivisible event stays in the same scope for recovery; do not invent token-only child ownership.
- All normal terminal states and output-limited states MUST enter the same artifact validation. Overlength, underlength, duplicate, corrupt, out-of-scope, or incomplete prose is not accepted merely because the provider reported a normal finish. Never mechanically truncate prose.
- Validate every leaf, merged parent, complete writing segment, and whole draft independently. Child success cannot substitute for parent or whole-story validation. Promotion requires exact event coverage and order plus consistent causality, StoryState, character and knowledge state, timeline, relationships, setup/payoff, handoffs, and confirmed ending.
- Semantic acceptance MUST be bound to the immutable authority and exact generated-text hash. Every claimed owned event, entry state, and exit state needs a verifier-provided excerpt that Runtime proves occurs in that exact text; copied plan metadata or self-declared event IDs without prose evidence are not acceptance receipts. Whole-draft reduction MUST preserve source hashes, covered ranges, and every prior issue identity deterministically.
- Token or context pressure may change the validation topology only. Use complete overlapping windows and hash-bound hierarchical evidence reduction when a whole-story check does not fit; sampling, omitted ranges, stale summaries, or an incomplete global adjudication MUST stop downstream work.
- Commit generated authority atomically. Failed or ambiguous validation may retain diagnostic output and valid upstream checkpoints, but it MUST NOT replace an accepted parent, segment, whole draft, quality checkpoint, candidate, or formal manuscript.
- A generated-subtask change is incomplete without regression tests for a stale parent target, recursive overlength, normal-finish invalid output, output-limited output, an indivisible event, child failure, merged-parent failure, whole-draft coverage failure, corruption, and full-coverage review under context pressure.

## Planning Adaptation Authorization Gate

- A running plan MAY enrich dialogue, description, transitions, minor actions or props, scene realization, trigger method, supporting participants, local location, evidence-acquisition method, and non-dependent micro-order without rewriting the formal outline. It MUST NOT change event function, primary-actor agency, causal dependencies, entry or exit state, knowledge or relationship state, viewpoint, dependency-sensitive chronology, setup/payoff, or the confirmed ending.
- Do not require literal copying when an implementation is narratively equivalent. Every non-literal implementation must instead pass a hash-bound review for each formal segment and a second whole-plan review for cross-segment causality, handoffs, state progression, viewpoint/timeline, promises, and ending.
- Review evidence must be selected from Runtime-owned exact plan excerpts. Prefer the smallest usable field or passage; do not authorize an entire multi-event plan segment when bounded evidence exists, and never let the model invent or paraphrase evidence.
- Receipt JSON, hash, coverage, label, or evidence-binding failures are protocol defects. Retry only the immutable receipt and do not mutate the plan or consume semantic-repair budget. A reported semantic drift must include an actionable affected segment and event scope.
- Repair semantic drift through a monotonic best-candidate ledger. Regenerate only the complete affected plan segments from the full failure receipt, preserving unaffected segments and current creative value. A candidate may replace the best plan only when its stable hard-issue set is a strict subset of the prior set and introduces no new hard issue. After two targeted attempts, rebuild only the still-affected complete segments from formal event contracts. A single residual issue MUST NOT trigger a free whole-plan rebuild. Re-run local structure, every hash-invalidated segment review, adjacent boundary review, and whole-plan review before promotion.
- Persist the best complete plan and its issue ledger before review and after every accepted candidate. Transport failure, truncation, malformed candidate output, protocol failure, cancellation, or process interruption MUST leave that hash-bound pair reusable by the next task. Recovery state is a checkpoint and audit ledger, never downstream narrative authority; the recovered plan must pass the current V2 segment and whole-plan authorization before drafting.
- Once authorized, the current plan realization is the sole downstream execution evidence. Retain formal evidence for audit, but never mix the old formal realization with the authorized current realization inside one execution manifest or draft task.
- `planning-adaptations.json` is a derived, hash-bound receipt rather than a second StoryState. Full and partial checkpoints that bind it must copy it losslessly and reject missing, stale, or tampered content; checkpoints created before this artifact existed remain compatible through their original authority chain.

## Resolution Completeness Gate

- Detecting, rejecting, checkpointing, rolling back, or stopping on an invalid artifact is failure containment, not problem resolution. Never describe a defect as fixed merely because the Runtime now fails closed or prevents downstream narrative damage.
- Every proposed fix MUST state an implementable recovery path: the root cause and affected boundary, the exact accepted input variants, the authoritative state retained, the smallest regeneration or deterministic repair scope, retry and fallback behavior, terminal behavior after exhaustion, and how downstream narrative authority is revalidated before continuation.
- Automatic repair MUST be regression-aware, not merely retry-aware. Compare every candidate with the last accepted complete scope: it may advance only when the targeted hard-issue set strictly shrinks or reaches zero, no new hard issue appears, unaffected material remains unchanged where deterministic ownership exists, and applicable prose-quality floors do not regress. A candidate that fixes A while breaking B is a business incident and MUST be rejected, audited, and restored to the prior best state.
- Every model-generated mutation, including schema repair, integrity repair, semantic repair, segment rebuild, targeted revision, split/merge, fallback, and resume, MUST re-enter the same ordered validation closure for syntax/schema, ownership and evidence, local semantics, adjacent handoffs, and whole-story integrity. A later repair is never trusted because an earlier version passed. A recoverable defect introduced by a later phase must not become terminal solely because that phase set schema or integrity recovery budgets to zero.
- A multi-cause narrative state MUST be represented losslessly or decomposed into independently attributable assertions. Do not force semantically valid composite causality into a scalar field, silently choose one producer, or discard contributing beats merely to satisfy a parser.
- Regression evidence for a fix MUST prove successful recovery of the production-shaped failure and successful continuation through the next authoritative boundary. Fail-closed coverage is necessary but insufficient. Include at least one test where a later repair reintroduces an earlier schema or integrity defect and the unified recovery loop resolves it without changing formal plot authority.
- User-facing diagnosis MUST distinguish containment from resolution and provide a concrete, executable solution. If a complete recovery cannot yet be implemented, state that the issue remains unresolved, identify the precise blocker, and do not claim completion.

## Granular Recovery Isolation Gate

- Every workflow that creates, repairs, reviews, merges, polishes, or revises more than one independently owned segment, packet, evidence group, or user-selected modification MUST define the smallest deterministic promotion unit before implementation. This applies to planning, causal-chain and manifest recovery, drafting and split/merge, ordinary polish, structural polish, review, targeted revision, and manual revision.
- A failed, incomplete, regressing, truncated, cancelled, or transport-interrupted unit MUST NOT automatically revoke another unit that already passed its local contract, adjacent handoff checks, and the applicable whole-story validation. Persist each accepted unit immediately in the monotonic best candidate and a hash-bound checkpoint so later work and later tasks can reuse it.
- Avoiding collateral rollback MUST NOT create an incoherent mixed manuscript. Promote a retained subset only after rebuilding the complete candidate from deterministic ownership, revalidating changed units, adjacent entry/exit boundaries, and the whole-story authority. If no safe subset exists, restore the last accepted complete scope and leave every rejected issue unresolved.
- Recovery budgets belong to the remaining failing units, not to an earlier batch that contained successful work. Strict progress over any unit refreshes the bounded repair ladder for the still-failing scope; repeated attempts MUST start from the latest accepted best candidate and MUST NOT reintroduce facts or prose from rejected candidates.
- Interruption and resume MUST preserve accepted unit decisions and invalidate only the failed unit and its deterministic dependents or suffix. A later-stage conflict in polish, review, targeted revision, or manual revision MUST be isolated with the same rule instead of rolling back unrelated accepted changes.
- Before changing any multi-unit workflow, explicitly assess whether the design can cause downstream collateral rollback. Regression coverage MUST include a production-shaped case where some units fix prior hard issues while another unit introduces new hard issues, and prove that the safe units survive across the next authoritative boundary, resume, polish, and targeted/manual revision without weakening narrative logic or user-selected scope.

## Model Context Capacity Gate

- Every new or changed prompt, retry, review, recovery ledger, whole-story check, and evidence handoff MUST estimate both input and output token pressure before implementation and before dispatch. A design with a credible provider context or output-limit risk is incomplete until it defines and tests a bounded execution topology.
- Full authority and diagnostic evidence MUST remain lossless in hash-bound persisted artifacts. A single model call receives only the complete authority and failure evidence relevant to its current semantic ownership; unrelated material is represented by stable IDs and hashes, never repeated raw text.
- If relevant material still approaches the configured safety range, split it by semantic ownership such as segment, event, issue group, evidence anchor, or complete overlapping review window. Each packet MUST bind the same authority, packet identity, coverage range, and predecessor state so interruption can resume without replaying accepted work.
- Token mitigation MUST NOT mechanically truncate prose, formal authority, failure evidence, causal state, or required cross-story coverage. It also MUST NOT lower quality by replacing authoritative text with a stale or lossy summary. Use deterministic projections, hash-bound hierarchical reductions, and a final full-coverage merge/adjudication instead.
- Provider output limits and context limits are runtime capabilities, not creative budgets. Retry with verified headroom when supported; otherwise reduce semantic scope while preserving the total requested work. A split changes call topology, not the story target, event ownership, or required final quality.
- Every split recovery or hierarchical review MUST prove complete packet coverage, no duplicate or missing ownership, safe merge, adjacent handoff consistency, and whole-story integrity before promotion. Network failure, truncation, or cancellation retains completed packets and the current best artifact for resumable continuation.
- Regression coverage MUST include production-shaped long prompts, many rejected candidates, large evidence receipts, an unknown provider limit, output truncation, interrupted packet execution, and successful continuation through the next authoritative boundary without losing creative material or narrative logic.

## New Feature Integration Gate

- New features must preserve the existing StoryState authority, Runtime-controlled formal writes, model roles and fallbacks, Skill behavior, candidate validation, quality gates, credentials, project files, and run history by default.
- Do not introduce a second authoritative state store, competing workflow, or direct model/Skill write path. Extend existing modules and contracts with the smallest compatible change.
- Existing projects and default behavior must remain unchanged unless the user explicitly enables the feature. Prefer project-scoped, reversible feature flags for optional behavior.
- Before adopting external code, prompts, Skills, or workflows, document overlap, prompt/Skill conflicts, data ownership, migration and rollback, security boundaries, and license obligations.
- A change may alter a core path only when it can materially improve writing quality, consistency, or user control. The proposal must state measurable acceptance criteria and preserve the old path as a tested fallback until comparative evidence confirms the improvement.
- New generated content must continue through the existing candidate, validation, review, and commit flow. No feature may overwrite a formal manuscript directly.
