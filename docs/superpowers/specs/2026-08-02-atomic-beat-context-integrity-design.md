# 原子剧情节拍与分层上下文完整性设计

日期：2026-08-02
修订：2026-08-03（跨题材事件视图与逐段执行索引）
状态：已批准

## 背景

短篇运行 `ffe02cf823674d24a48a427acc234ace` 暴露了两个相互关联的问题。

第一，正式大纲中的一个粗粒度事件可能同时包含多个可执行动作。当前规划只给整个事件分配一个事件 ID，却允许段末交接从该事件中抽取部分动作。生产规划把 `EV-8E4BBA17` 分配给第 2 段，同时要求第 1 段完成其中的“沈老夫人派人外出核实身份”。正文模型因此同时收到“不得提前写后续事件”和“必须完成后续事件的一部分”两条冲突指令。

第二，正文阶段当前直接加载完整约束和完整 Skill 提示。本次请求包含约 41,144 个约束字符、20,837 个 Skill 提示字符和约 34,827 个输入 token。请求没有截断，但模型把正式的第一人称要求写成第三人称，并在宴厅、府门和屋内之间产生顺序回退。这说明上下文可装入供应商窗口不等于模型能稳定服从所有混合指令。

## 目标

1. 正式大纲、StoryState、确认结局和项目资料保持唯一叙事权威，自动修复不得修改它们。
2. 将粗粒度正式事件展开为稳定的原子剧情节拍，每个节拍恰好由一个写作段负责。
3. 段末交接只能描述本段已拥有节拍产生的状态；下一段只能继承状态，不能重复执行动作。
4. 在正文生成前检测事件证据、执行者、所有权、入口、出口、展示顺序和跨段冲突；结构、边界与语义使用独立修复额度。
5. 正文、润色、审核和返修统一使用分层、去重、哈希绑定的上下文包；不可因压缩遗漏硬约束。
6. 语义失败按根因恢复：规划冲突回到规划层，模型不服从则完整重写当前段，网络和输出限制沿用既有恢复规则。
7. 旧规划、旧执行索引和失败正文不得绕过新门禁；有效上游检查点继续复用。
8. 所有自动化测试使用假模型或纯函数，不调用付费模型。

## 非目标

- 不重新生成或静默改写用户确认的正式大纲。
- 不通过机械截断提示词、正文或降低输出 token 来解决注意力问题。
- 不把原子节拍变成正文段落模板；节拍只属于控制和验收层。
- 不承诺模型永不犯错；系统承诺错误不经验证进入后续流程。
- 不建立第二套 StoryState 或正式稿存储。

## 一、权威层级

权威顺序固定为：

1. 正式大纲、锁定事实、确认结局和 StoryState；
2. 由正式资料哈希绑定的短篇因果链；
3. 原子节拍执行清单；
4. 当前段任务契约；
5. 已验收正文及其语义回执；
6. 建议级写作方法和市场信息。

自动修复只能重建第 3、4 层。若第 1、2 层自身矛盾或缺失，程序保留已有资料并在正文前停止，不能猜测性修复故事事实。

## 二、原子剧情节拍执行清单

### 1. 数据结构

`short-execution-index.json` 升级为版本 3，并在现有权威字段之外保存：

- `outline_sha256`、`planning_sha256`、`causal_chain_sha256`；
- 有序 `beats`；
- 有序 `segments`；
- 独立语义验收回执；
- 自动修复次数和最终状态。

每个原子节拍至少包含：

- 稳定 `beat_id`，格式为 `EV-XXXXXXXX/NN`；
- `source_event_id`；
- 全篇顺序；
- 必须实际发生的动作；
- 动作发生前的前置状态；
- 动作产生的后置状态；
- 唯一 `owner_segment`；
- 对应正式大纲或规划的原文证据。
- `presentation_order`，由 Runtime 在合并时连续绑定；
- 可选 `story_time`、`timeline`、`actor`、`location`、`viewpoint`、`knowledge_delta` 和 `relationship_delta`。

版本 3 不把标题文本天然视作剧情事件。Runtime 先从正式大纲派生只在当前运行中使用的事件视图：Markdown 层级中拥有具体子事件的章节、幕、卷、篇、阶段、Act、Chapter、Phase 等标题是结构容器；没有具体子事件的稀疏标题才作为兜底事件。正式大纲文件、持久事件 ID 和 StoryState 均不改写。每个事件合同保留精确原文块，节拍证据必须属于其声明的事件块，而不是仅仅出现在整份大纲的其他位置。

版本 4 将段末状态的 `produced_by` 规范化为有序节拍 ID 数组。一条状态由多个连续节拍共同形成时必须无损记录全部来源；旧版单字符串以及模型返回的中英文逗号、分号或顿号分隔形式可在统一解析边界规范化。非节拍标签不能作为生产者。段前已经成立的事实必须进入 `entry_state` 并通过 `inherited_from` 继承，不能伪装成当前段新产生的出口状态。版本 2、3 继续按各自旧表示计算哈希，读写往返必须幂等。

每个写作段至少包含：

- 有序 `beat_ids`；
- 段首状态；
- 段末状态；
- 每条段末状态的全部 `produced_by` 节拍；
- 上一段出口哈希；
- 下一段禁止提前消费的节拍。

### 2. 结构验证

Runtime 必须确定性验证：

- 所有正式叙事事件至少展开为一个节拍；
- 节拍 ID 唯一且顺序稳定；
- 每个节拍恰好只有一个负责段；
- 每段节拍是全篇节拍的连续有序子序列；
- 不存在缺失、重复或倒序节拍；
- 段末每个新动作或状态都有一个或多个本段 `produced_by`，且共同原因不得丢失；
- 下一段入口与上一段出口一致，但不重新拥有生产该状态的动作；
- 正式大纲、因果链和规划哈希与当前项目一致。
- 节拍证据位于对应事件合同内；
- 展示顺序连续且与规划一致，倒叙和多时间线不按故事内时间强制重排；
- Runtime 合并后重新编号全局节拍、绑定上一出口哈希并计算完整的未来节拍禁止列表。

### 3. 语义验证

自然语言中的动作、执行者和状态不能只靠字符串比较。每个正式写作段的 fragment 通过本地结构和边界检查后，独立 Review 路由返回哈希绑定的验收回执，逐项提供正式资料原文证据并判断：

- 动作没有改变执行者、对象、时间或结果；
- 段末状态确实由本段节拍产生；
- 没有把未来节拍伪装成当前交接；
- 相邻段入口和出口语义一致；
- 原子化没有改变正式剧情。

Runtime 校验所有哈希、ID、证据原文和覆盖范围，不能直接信任模型布尔值。

初次生成、结构修正、完整性修正、语义最小修正和完整段重建都必须进入同一个验证闭环：JSON/结构、事件所有权与证据、局部语义、相邻入口/出口、整篇完整性。语义返修不得将结构或完整性恢复次数设为零；后期返修重新引入较早阶段错误时，Runtime 必须按错误类别继续有界恢复。只有成功恢复并通过下一权威边界才算问题解决，安全停止只算故障隔离。

Review 提示明确提供 Runtime 已计算的 `EXPECTED AUTHORITY SHA256` 与 `EXPECTED MANIFEST SHA256`，模型只负责原样回填。节拍证据由 Runtime 直接绑定已验证的 `source_evidence`；分段边界证据由 Review 选择 Runtime 提供的候选 ID，再映射回规划原文。Markdown、空白、换行或包装差异只能触发确定性展示归一化，不能让模型自由改写、拼接证据。校验器一次汇总哈希、节拍覆盖、执行者/动作、边界、原文证据和 `formal_plot_unchanged` 的全部独立错误。全部 fragment 通过后，Runtime 无损汇总逐段回执，再对合并后的整篇清单执行覆盖、展示顺序、相邻状态和禁用范围核验；不再要求单次模型调用审核整份超长清单。

### 4. 自动修正规划

每个正式段独立生成。结构/JSON schema 最多自动修复两次，事件覆盖/证据/边界最多自动修复两次，两类额度互不挤占。审核回执自身的 JSON、哈希、覆盖、摘要或证据绑定错误使用独立的三次协议预算，只重新获取并确定性绑定回执，不修改 fragment，也不消耗语义修复额度；协议耗尽时保留 `content_valid` 清单并停止正文。只有明确否定执行者、动作、地点、前后状态、视角、时间线、知情或关系字段时才进入两级语义恢复：先按字段级错误和审核原因最小修正错误节拍，再重建受影响的完整正式段 fragment。修复只能调整运行时节拍拆分、负责段、入口和出口，不得修改正式大纲内容。

两级语义恢复仍失败时停止在规划阶段，记录全部冲突，不启动正文；已经通过的较早 fragment 继续保留为哈希绑定检查点。版本 2 和 3 仍可被旧正文、润色、返修和检查点读取，且维持各自历史摘要算法，但不能驱动新的短篇规划；再次运行时幂等重建版本 4。缺少验收回执的索引同样自动重验或重建。

### 5. 规划等价展开授权

正式大纲继续定义剧情功能和不可变结果，但运行规划不再被要求逐字复制大纲中的唯一实现。对话、描写、过渡、次要动作与道具、场景表现、触发方式、次要参与者、局部地点、证据取得方式，以及不改变依赖关系的局部顺序，可以作为表现层或等价展开。事件功能、主要执行者主动性、因果依赖、入口/出口、知情与关系状态、视角、依赖性时间顺序、伏笔兑现和确认结局仍是结构不变量。

本地结构门禁通过后，Runtime 对每个正式写作段执行一次独立适配审核，再对完整规划执行一次跨段审核。逐段回执绑定正式大纲哈希、规划哈希、段号、事件合同和当前规划段；证据只能从 Runtime 给出的有界原文候选中选择。整篇回执继续绑定全部逐段回执，并核对跨段因果、相邻交接、知情、关系、视角/时间线、伏笔和结局。一个正式事件连续跨越多个分段时，其各段证据按顺序无损合并，不能只保留第一段证据。

回执格式、哈希、覆盖、标签、证据 ID 或受影响范围不一致属于协议失败，只重取回执，不修改规划，也不消耗语义恢复额度。有语义偏移时，回执必须给出可执行的最小分段和事件范围。Runtime 先按完整失败回执依次重建所有受影响的完整规划段；每次替换保持其他段原样，并让后一个受影响段读取前一个修正后的出口。任一段返回不完整，或合并后仍不通过逐段/整篇审核，则从正式事件合同重建完整运行规划。两个恢复层级都必须重新经过本地结构、逐段适配和整篇适配闭环，不能以拦截代替解决。

通过后的 `planning-adaptations.json` 是派生、哈希绑定的审核回执，不是第二套 StoryState。下游执行索引只使用已授权的当前规划实现作为 `evidence`，同时保留正式大纲原文为 `formal_evidence` 供审计；同一任务内禁止把旧实现与当前实现混写。适配哈希进入执行 authority、完整检查点和部分检查点。绑定该哈希的新检查点缺失或篡改适配文件时失效；没有适配哈希的历史检查点继续沿用原 authority，无需迁移正式大纲或项目资料。

## 三、分层上下文包

### 1. 上下文层

所有影响叙事的模型调用统一装配以下层：

1. 当前唯一任务契约；
2. 全篇硬性叙事不变量；
3. 当前原子节拍、入口和出口；
4. 上一已验收出口及必要正文尾部；
5. 下一段入口及禁止提前消费节拍；
6. 当前涉及人物、地点、伏笔和文风的原始资料；
7. 哈希绑定的全篇节拍骨架；
8. 当前阶段适用的 Skill 规则；
9. 建议级材料。

优先级按上述顺序固定。当前任务契约和硬性叙事不变量不得被建议级内容覆盖。

### 2. 硬规则注册表

约束和 Skill 提示先进入规则注册表。每条规则保存稳定 ID、原文、来源哈希、适用阶段、适用范围和优先级。以下内容永远属于硬规则：

- 叙述视角、时态和语言；
- 锁定人物、关系、知识边界和世界规则；
- 正式事件、因果和确认结局；
- 当前任务入口、出口、所有权和禁止范围；
- 用户明确要求的不可变内容。

完全相同的规则按规范化指纹去重。压缩只允许移除示例、重复说明和当前阶段无关建议，不得删除硬规则。装配后 Runtime 逐个核对硬规则 ID；任何缺失都在调用前失败。

### 3. 动态压力处理

程序分别记录任务、硬规则、全篇骨架、相关原文、Skill 和建议的 token。供应商上下文已知时，输入加输出预留接近物理窗口会触发分层或语义拆分；上限未知时不猜测能力，但仍执行去重和相关性装配。

无论上下文窗口多大，正文阶段都不再默认塞入所有原始约束和完整 Skill 示例。若硬权威本身仍无法安全放入一次调用，程序按语义范围拆分任务或核对窗口，不能抽样或截断权威。

## 四、正文生成与自动恢复

正文任务契约从版本 3 执行清单构建，使用原子节拍 ID，而不是只使用粗粒度正式事件 ID。模型只能生成当前段连续节拍。读取历史质量稿时仍兼容版本 2。

语义回执新增：

- 每个原子节拍的精确正文证据；
- 段首和段末状态证据；
- 叙述视角判定及证据；
- 人物位置、时间和知情状态；
- 执行者一致性；
- 场景顺序；
- 是否提前消费未来节拍。

恢复按根因分流：

- 执行清单矛盾：返回规划层自动修复，不消耗正文重试次数；
- 模型漏写、改执行者、视角错误或场景回退：携带失败证据完整重写当前段；
- 网络中断：同上下文、同任务契约重试；
- 输出限制：增加输出空间，仍不足时按原子节拍拆分；
- 两次同范围语义重写仍失败：保留已验收上游进度并停止。

禁止通过追加一句话、局部拼接或机械替换来伪造出口状态。每次重写后生成新的正文哈希并重新执行全部验收。

## 五、后续流程

### 润色与返修

润色和返修读取当前段原子节拍回执、上一出口、下一入口、硬规则和允许修改范围。结果必须重新通过视角、节拍、执行者、场景状态和边界检查。失败结果不得覆盖原文；必要时完整重写当前润色窗或保留已验收原文。

### 审核

分层审核继续使用哈希绑定窗口和无损证据合并。每个窗口同时获得全篇节拍骨架和当前覆盖节拍。全局归并必须确认所有节拍、入口、出口、人物弧、伏笔和结局，不能只依赖摘要定案。

### 整篇验收

整篇完成后，Runtime 先确定性验证节拍清单、段哈希和回执覆盖，再执行分层语义审核。只有全事件一次覆盖、因果顺序、视角、人物状态、承诺和结局全部通过，正文才能进入候选稿和发布流程。

## 六、检查点与兼容性

- `short-execution-index.json` 版本升级到 3；版本 1 必须重验，版本 2 可读取但新规划必须幂等重建。
- 正文检查点升级到 3，必须包含执行清单哈希、原子节拍 ID 和语义回执。
- 失败正文可作为诊断输出保存，但不能成为有效检查点。
- 正式大纲、因果链、StoryState、人物资料、模型绑定、Skill、历史运行和正式稿不迁移、不覆盖。
- 已验收段只有在正式资料、执行清单、上一出口和正文哈希全部匹配时才可复用。
- 从第一个失效段开始重做，之前仍有效的段继续复用。

## 七、运行日志

日志必须区分：

- 规划事件所有权冲突；
- 自动修正规划第几次；
- 上下文各层字符和 token；
- 去重和省略的建议级内容；
- 缺失硬规则导致的调用前停止；
- 正文视角、节拍、执行者、入口、出口或场景顺序失败；
- 当前完整重写次数；
- 已保留的有效检查点和重做起点。

用户可见错误不能只显示首个字段。一次验收中的全部独立失败项应同时记录并显示。

## 八、验收标准

1. 生产失败样例中的“派人核实”和“发现二十两”被拆成两个唯一节拍，不再形成跨段所有权冲突。
2. 版本 1、2 执行索引不能直接驱动新的短篇规划；版本 3 保持可读和哈希兼容，新生成的版本 4 清单通过逐段及整篇结构和语义验收后才能开始正文。
3. 第一人称硬约束在正文、润色、审核和返修上下文中始终存在，并可由清单验证。
4. 重复 Skill 和约束规则只发送一次，示例和无关建议可省略，硬规则零遗漏。
