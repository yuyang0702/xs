# 项目文风感知校验与安全精修恢复设计

## 目标

本次改造解决两个已经在生产任务中出现、并会相互放大的问题：

1. 本地文笔指标统计错误和固定阈值会把符合项目文风的精修稿误判为退化稿；
2. 普通精修把输出触顶、输入过长、网络中断和本地校验失败混在同一条“精简后重试”路径中，导致不必要的上下文删减，并绕过了已经具备的语义拆分能力。

最终目标不是让任务尽量继续，而是在不牺牲整篇小说逻辑、人物状态、因果链、伏笔兑现和已确认结局的前提下，提高跨小说、跨文风、跨模型供应商的兼容性。任何恢复结果仍须经过现有候选稿、校验、复核和正式提交链路；原稿始终是失败时的安全底线。

## 与现有设计的关系

- 本设计细化并落实 `2026-08-02-adaptive-output-and-semantic-task-splitting-design.md` 在普通精修阶段的行为。
- 本设计取代 `2026-07-30-polish-recovery-loop-design.md` 中“输出触顶后改用精简提示且不拆分”的旧决策。输出触顶改为“同路由增加输出余量一次，再按语义拆分”。
- 不改变 StoryState、正式大纲、因果链和正式稿的权威关系，不增加第二套剧情状态。
- 不调用付费模型进行探测或自动化测试。

## 强制约束

1. 任何流程、重试、备用模型、精简、拆分和恢复都必须保持整篇小说的因果、人物位置与知识状态、时间顺序、关系进展、伏笔与兑现、保护内容和确认结局。
2. 项目文风只能覆盖通用的软风格阈值，不能覆盖损坏、截断、重复、事实冲突、事件丢失、越界、连续性矛盾等硬错误。
3. 当前完整源段、最小叙事权威包和必要输出余量无法共同放入请求时，必须按语义拆分；禁止继续删除权威信息以勉强塞入请求。
4. 不完整子段、局部成功结果和未通过父段合并校验的结果不能成为正式权威。
5. 旧项目不强制迁移、不自动改写现有文风资料、不改变已完成运行和检查点。

## 一、统一失败分类

每次模型调用和本地校验分别分类，禁止使用一个异常类型同时表示多种问题。

### 1. 模型调用分类

- `input_context_overflow`：请求上下文超过供应商或模型窗口。
- `output_limit`：供应商明确报告输出达到限制，或结束状态证明工具协议/正文被截断。
- `transport_interrupted`：网络断开、超时、502/504、连接失败等传输问题。
- `normal_invalid_output`：调用正常结束，但正文为空、格式错误、内容不完整或未满足工件协议。
- `provider_rejection`：鉴权、额度、安全策略或配置错误。

### 2. 本地校验分类

- `hard_integrity`：损坏、截断、大段重复、保护内容丢失、事件越界、事实或连续性冲突。
- `soft_style`：短句比例、段落节奏、句式同构、对白密度等风格偏移。
- `uncertain_style`：样本不足、文风规则冲突或无法确定场景是否授权某种节奏。

模型调用失败不能伪装成本地质量失败，本地风格失败也不能触发供应商容量熔断。用户事件必须显示实际类别。

## 二、最小叙事权威包

所有完整提示、精简提示、备用模型调用和拆分子任务都通过同一个构建器取得权威包。该权威包至少包含：

- 当前源段完整文本；
- 当前段拥有的正式事件 ID、因果目标和允许修改范围；
- 前一已接受段的结尾、退出状态和交接；
- 下一源段的入口、不可提前进入的事件和交接要求；
- 相关人物的位置、关系、知识边界、动机和声音指纹；
- 锁定事实、结局约束和保护内容；
- 与当前段有关的伏笔、兑现、悬念和承诺；
- 项目文风规则及当前场景允许的节奏方式；
- 约束、StoryState、正式计划和检查点所需的版本或哈希。

完整提示可以额外携带全局建议、更多上下文和示例。精简提示只能移除重复说明、无关人物、远距离背景、非命中问题和冗长示例，不能删减上述权威包。

构建完成后执行字段完整性检查。缺少、冲突、过期或无法容纳的必需字段不允许进入模型调用。

## 三、输入压力、动态输出余量与供应商未知上限

### 输入压力

只有输入压力可以触发精简：

1. 已知模型上下文窗口时，估算系统提示、Skill、约束、用户提示、协议开销和输出预留；预计占用达到窗口约 75% 时优先去除非权威冗余，达到约 80% 且权威包仍无法安全容纳时直接拆分。
2. 未知上下文窗口时不猜测物理上限，也不提前删减。先发送完整权威请求；只有收到明确的上下文超限、请求过大或 413 类错误时才进入精简或拆分。
3. 同一路由在当前运行中重复发生明确输入超限时，可以对后续相似段打开“输入精简熔断”，但熔断不得由输出触顶、网络错误或本地风格失败触发。

Token 估算覆盖实际发送的系统、用户、Skill、约束和工具协议。隐藏推理无法在调用前精确计算，因此不伪造精确预测；它通过供应商返回的输出消耗和路由历史作为输出余量风险处理。

### 动态输出余量

- 用户配置的 `max_tokens` 是该阶段的基准，不是必须压低质量的硬上限；程序可为完整工件自动提高请求额度。
- 提高额度受供应商明确能力、模型元数据、剩余上下文和已观察到的安全下界约束。
- 未知供应商不通过付费探针发现上限。正常完成只能证明该路由至少支持本次用量；明确的上限错误和重复触顶用于形成保守观察，不把网络错误当成容量证据。
- 如果供应商报告消耗大量输出 Token 但可见正文为空，视为输出风险。先按同一路由增加余量一次；仍失败则语义拆分或使用配置的备用路由，不能通过删除叙事上下文来解决。

## 四、项目文风感知的分层校验

### 1. 修正客观指标

统一句子边界统计，正确处理：

- 中文和英文句号、问号、叹号；
- 句末引号、括号和省略号；
- 多句同段、单句成段和对白段；
- CRLF/LF、空行、全角/半角标点和常见 Markdown 包装。

生产故障的最小样例必须加入测试：一个自然段包含多个普通中文句子时，每个终止标点都应计数，不能只计算位于引号或段尾的标点。

### 2. `ProseValidationPolicy`

在运行时解析一个只读的项目校验策略。它不是剧情权威，也不新建数据库表。策略来源优先级固定为：

1. 用户明确锁定的文风和保护要求；
2. 项目 `style-profile.md` 与已确认、已应用的 `prose_baseline`；
3. 已采用的创作蓝图和人物声音资料；
4. 通用默认文风；
5. 市场与参考资料只提供建议，不能授权覆盖前四项。

新版本 `prose_baseline` 可以选择性携带结构化 `validation_policy`，旧文件缺失时按兼容路径读取，不自动回填。自由文本只有在规则明确、无冲突且能映射到已记录的策略类型时才能授权软阈值；含糊或相互冲突的规则只产生 `style_policy_conflict` 警告，不能放宽。

策略描述句段节奏模式、允许短句聚集的叙事节点、对白处理方式、保护范围、来源和规则 ID。授权节点由正式事件和状态变化判断，例如知识揭示、关系变化、动机变化、伏笔兑现、悬念建立或情绪转折，不能仅靠“突然”“真相”等题材词汇猜测。

### 3. 动态阈值

软风格阈值使用以下基线：

- 当前源段；
- 相邻已通过段落；
- 最近 3 至 5 个可比较的已通过段落；
- 项目校验策略。

样本足够时使用中位数和稳健离散度计算边界；样本不足时只做源段与相邻段比较。默认信号要求同时满足：

- 比例偏移达到约 10% 的绝对保护带或超出项目稳健边界；
- 至少新增 3 个相关短句或段落单位；
- 异常不完全位于项目明确授权的叙事节点。

阈值只用于发现风险，不是模型必须追逐的写作目标。全局比例不能单独拒绝候选稿。

同一证据产生的 `one_sentence_paragraph_run`、`short_sentence_ratio`、`sentence_rhythm_regression` 和 `style_regression` 归并为一个“节奏信号族”，禁止重复计罚。

### 4. 校验结果

- `pass`：硬校验通过，软指标在基线内。
- `pass_with_style_allowance`：通用指标偏移，但被明确项目规则和对应叙事节点授权。
- `targeted_repair`：硬校验通过，但至少两个独立软信号族异常，或一个未被授权的大范围严重分布异常。
- `reject`：任一硬完整性错误。

大范围严重分布异常需要结合覆盖范围和连续区域判断，不能只由某个比例决定。未知文风不自动放宽；证据不足时保留原文或进入人工可解释的定点修复，而不是把猜测当授权。

## 五、普通精修恢复状态机

每个父段按以下顺序执行：

1. 组装完整源段和最小叙事权威包。
2. 输入安全时调用主路由；已知输入压力时去除非权威冗余，权威包仍不适配则语义拆分。
3. 模型正常返回后运行硬校验、项目文风校验和上下文交接校验。
4. `pass` 或 `pass_with_style_allowance`：保存为已验证候选检查点。
5. `targeted_repair`：只发送问题证据附近的范围、必要上下文和完整适用权威；不得重写整段。主路由失败后可使用配置的备用路由。仍未通过则保留整个父段原文。
6. `reject`：丢弃候选，保留整个父段原文；事实和连续性硬错误不能通过风格修复掩盖。
7. 明确输入超限：先删非权威冗余；权威包仍超限则语义拆分。
8. 明确输出触顶：同一实际路由提高输出余量重试一次；仍不完整则语义拆分。输出触顶不进入精简提示熔断。
9. 网络中断：同一路由重试一次，再使用配置的备用路由；不改变容量观察，不删减上下文。所有重试继续绑定同一权威包和检查点。

## 六、语义拆分与父段原子提交

拆分优先选择：

1. 当前父段拥有的连续事件 ID；
2. 因果链环节；
3. 正式计划的场景边界；
4. 原文自然段和入口、冲突、状态变化、出口等叙事节拍。

不得在句子中间或固定字符位置硬切。每个子段都接收父段适用的权威信息、自己的事件所有权、前一已接受子段的退出状态，以及下一子段不可提前进入的入口。

所有子段只作为临时检查点。只有在以下条件全部成立后，父段才成为已验证候选：

- 每个子段分别通过硬校验和适用的文风校验；
- 子段之间人物、地点、时间、知识、动机和事件顺序一致；
- 合并后没有重复、缺失、越界、接缝突变或保护内容丢失；
- 合并父段重新通过完整性、事件覆盖、交接和项目文风校验。

任一子段最终失败时，整个父段保留原文。已成功子段可以作为同一权威版本下的非正式检查点复用，但不能单独写入正式稿。权威哈希变化时，从变化点开始的子段检查点全部失效。

## 七、跨流程兼容要求

本次普通精修改造使用共享分类和权威包接口，后续流程不得自行重新解释同类错误：

| 流程 | 允许拆分边界 | 不能降级继续的内容 |
| --- | --- | --- |
| 规划 | 连续正式事件、场景组 | 事件覆盖、顺序、交接、结局约束 |
| 因果链 | 事件范围、因果环 | 因果闭合、精确事件覆盖；未完成时禁止正文开始 |
| 正文 | 事件、因果环、场景节拍 | 人物/知识状态、前后交接、目标结局 |
| 精修 | 源段事件、自然段、叙事节拍 | 原文事实、保护内容、边界状态 |
| 审核 | 审核窗口、问题族 | 全窗口覆盖、证据和最终汇总结论 |
| StoryState/资料提取 | 独立事实批次 | 冲突检查和原子写入，禁止部分事实入库 |
| 长篇章节 | 章节计划场景、卷级事件 | 上章状态、卷目标、未兑现承诺 |

共享规则只统一失败分类、解析兼容、权威保留和提交边界，不强迫所有阶段使用相同文本阈值或相同拆分粒度。

## 八、运行事件与用户反馈

事件应明确说明：

- 是输入过长、输出触顶、网络失败、本地硬错误还是项目文风软偏移；
- 使用了哪个基线和项目规则；
- 哪些具体句段触发了问题；
- 是完整重试、定点修复、语义拆分、备用模型还是保留原文；
- 子段进度、父段是否已经整体通过，以及后续是否会继续。

页面可以使用简洁中文，例如“输出未完整，正在增加余量重试”“权威上下文无法安全容纳，正在按两个叙事节拍处理”“该短句节奏符合项目已确认文风，已通过”。内部事件元数据保留稳定错误码、指标、策略来源、证据范围、路由观察和哈希，便于复现。

## 九、兼容与迁移

- 不新增第二个状态库或调度器。
- `ProseValidationPolicy` 优先在运行时从现有资料派生；可选字段缺失时使用旧项目兼容路径。
- 不批量重写旧 `prose_baseline`、`style-profile.md`、运行记录或检查点。
- 如果实现中新增可选项目字段，读取必须向后兼容，写入只发生在用户下次明确应用新文风版本时，并补充幂等迁移或版本测试。
- 旧检查点仍可读；只有其权威哈希与当前资料一致时才能复用。
- 保留原有安全路径作为失败回退：候选不可证明安全时保留源段，不覆盖正式稿。

## 十、回归测试

### 客观指标

- 表驱动覆盖中文/英文/全角标点、引号、括号、省略号、多句同段、对白、CRLF/LF、空行和常见包装。
- malformed 和 ambiguous 输入保守失败或产生警告，不能静默选择错误解释。
- 固化本次生产误判的最小复现。

### 策略优先级

- 用户锁定规则覆盖通用软阈值。
- 已应用文风基线可以授权特定叙事节点。
- 市场建议不能覆盖项目文风。
- 含糊或冲突规则不能授权放宽，并产生可解释事件。

### 跨小说和跨文风

- 快节奏网文在授权转折处使用短句可以通过。
- 同样的碎片化出现在普通说明段时进入定点修复。
- 长句抒情文本、对白密集文本不被通用短句规则误杀。
- 古言、现代、悬疑、科幻、玄幻、梦境和虚拟场景不依赖题材关键词得出结论。

### 硬完整性

- 在任何策略下，截断、损坏、重复、保护内容丢失、事件缺失或越界、人物知识和连续性矛盾始终拒绝。
- 文风授权不能改变硬错误结果。

### 精简、输出恢复和拆分

- 所有精简路径完整保留最小叙事权威包。
- 权威包无法容纳时拆分，不进一步删减。
- 明确输入超限触发精简；输出触顶、网络错误和软校验失败不触发精简熔断。
- 输出触顶先增加同路由余量，再语义拆分。
- 网络中断同路由重试后走备用路由，且不污染供应商容量观察。
- 所有子段和合并父段通过后才产生授权检查点；子段部分成功不能覆盖原文。

### 生产回归与全量验证

- 固化当前第 2 至第 6 段的指标快照：修复计数后，第 3、6 段不再因错误的单句段连续计数失败；其余段按项目文风和实际分布判断，不能直接硬编码为通过。
- 运行事件能准确区分输出触顶、精简、拆分、定点修复和保留原文。
- 聚焦测试通过后运行完整测试套件；全部使用假模型和假供应商，不产生付费调用。

## 十一、实施顺序

1. 先修正句子与段落统计，并固化生产最小复现。
2. 增加独立的项目文风策略解析和优先级测试。
3. 将精修候选校验重构为分层结果，合并重复信号族。
4. 建立最小叙事权威包构建与完整性检查。
5. 分离输入压力、输出触顶、网络错误和本地校验的恢复状态机。
6. 把普通精修接入同路由增额、语义拆分、父段原子校验和检查点复用。
7. 补充运行事件和页面文案，使失败原因可解释。
8. 更新 `README.md` 或 `docs/maintenance.md`，记录解析兼容、文风优先级、精简触发和拆分规则。
9. 运行聚焦回归，再运行完整测试套件；确认无活动任务后才考虑重启服务。

## 十二、验收标准

本次实现只有同时满足以下条件才算完成：

- 多句中文段落统计正确，生产误判可复现且已消除；
- 项目明确软文风可以覆盖通用软阈值，硬完整性错误永不被覆盖；
- 固定 5% 单指标拒绝被源段、邻段和项目历史驱动的多证据判断取代；
- 同一节奏证据不再重复计罚；
- “正在精简要求”只在真实输入压力下出现；
- 输出触顶自动增加同路由余量，仍不完整时真正进入语义拆分；
- 网络失败按传输恢复处理，不误触发精简或容量熔断；
- 精简、备用模型和拆分都保留完整最小叙事权威包；
- 子段只有在父段合并校验通过后才能成为权威，任何失败均安全保留父段原文；
- 旧项目、旧检查点、模型绑定、Skills、运行历史和正式稿保持兼容；
- 用户日志能清楚解释失败类别、证据、恢复动作和最终结果；
- 聚焦测试与完整测试全部通过，且没有任何付费模型调用。
