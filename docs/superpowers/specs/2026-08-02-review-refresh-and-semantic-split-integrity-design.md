# AI 复检刷新与语义拆分完整性设计

日期：2026-08-02
状态：已批准

## 背景

当前候选稿质量区会从最新终审记录生成“最需要处理的问题”，但已解决问题仍可能留在该区域或继续计入总数。重新 AI 检测还缺少一条明确的原子刷新规则：新结果必须与当前稿件绑定、逐项核对旧问题并完整通过后，才能替换上一次有效结果。

短篇正文的自动拆分还存在目标继承缺陷。父任务拆成子任务时，内部 `target` 会变化，但递归调用继续沿用包含父级字数目标和完整事件范围的原提示词。正常结束的子任务只检查过短，没有立即检查过长。生产运行因此出现两个目标约 541/542 字的叶子任务分别返回约 1027/1132 个汉字，合并后达到 2159 字，却仍按父级 1083 字验收并被迫停止。

## 目标

1. 重新 AI 检测成功后，“最需要处理的问题”只显示当前仍可操作的问题，并同步重新排序。
2. 已解决问题立即移出优先清单，但保留在可追溯的“已解决记录”中。
3. 失败、截断、缺少旧问题对账或绑定了旧稿件的检测结果不得覆盖上一次有效记录。
4. 每次语义拆分都生成无冲突的当前目标、事件范围、入口状态和出口要求。
5. 无论拆分多少层，子任务、合并节点、完整写作段和整篇正文都必须逐级验证；叶子通过不能代替父级和整篇验证。
6. token 或供应商限制只能改变核对任务的执行形态，不能把全覆盖核对降级为抽查。
7. 保留现有 StoryState、正式大纲、因果链、执行索引、质量检查点和候选稿提交流程作为唯一权威，不引入第二套状态系统。

## 非目标

- 不通过机械截字解决子任务超长。
- 不因单个子任务略微偏离目标就牺牲完整场景或因果推进。
- 不让检测、拆分或核对流程直接覆盖正式稿。
- 不重写整个工作流调度器。
- 自动化测试不得调用付费模型。

## 一、检测结果契约

### 1. 权威绑定

一次可提交的 AI 复检结果必须包含并通过以下校验：

- 当前候选稿 SHA-256；
- 当前评分配置和终审模型签名；
- 本次检测标识及完成时间；
- 上一次有效问题清单；
- 每一个旧问题恰好一条对账结论；
- 本次新发现的问题；
- 完整、可解析且未被输出上限截断的终审结果。

稿件哈希、评分配置或模型结果不匹配时，本次结果仅作为失败运行证据保存，不得成为当前质量权威。

### 2. 问题状态

活动问题只包含：

- `unresolved`：仍未解决；
- `partially_resolved`：部分解决；
- `uncertain`：需要复核。

以下状态不进入“最需要处理的问题”：

- `resolved` / `closed`：已解决；
- `preserved`：已确认保留原写法。

已解决和已确认保留的问题进入历史记录，保存问题 ID、原始证据、最新复核证据、处理结论、稿件哈希和复检时间。历史记录仍属于现有质量检查点，不建立新的权威存储。

### 3. 对账与原子提交

旧问题不得因为模型遗漏而自动视为解决。对账必须满足：

- 每个旧问题 ID 出现且只出现一次；
- 状态属于允许集合；
- 已解决结论包含当前稿件中的复核证据；
- 未解决或待确认问题保留原问题身份和必要证据；
- 新问题使用稳定 ID，并与旧问题显式区分。

系统先在内存中构造新的活动问题、历史问题、分数和发布权限，全部验证通过后一次性写入质量检查点。任何一步失败都保留上一次有效检查点，并在界面上标明“本次复检未完成，当前显示上一次有效结果”。

### 4. 展示规则

“最需要处理的问题”的标题数量、列表内容和修复选择必须使用同一个活动问题集合。排序顺序为：

1. 必须处理且未解决；
2. 严重程度；
3. 未解决、部分解决、待确认；
4. 稳定问题 ID。

已解决记录单独折叠展示，不参与待处理数量、发布阻断或默认修复选择。

## 二、语义拆分契约

### 1. 拆分清单

每个父任务和子任务都要有可验证的拆分清单，至少包含：

- 权威资料哈希；
- 父任务 ID、子任务 ID、顺序和拆分深度；
- 当前唯一有效的目标字数及允许范围；
- 唯一负责的正式事件 ID 和因果步骤；
- 段首人物位置、动作、关系、时间和知情状态；
- 必须达到的段末交接状态；
- 前一个已验证兄弟任务的正文哈希和出口状态；
- 当前验证状态。

子任务提示词必须根据拆分清单重新构造。不得在含父级目标和完整事件范围的旧提示词后继续追加子任务说明。一个调用中只能存在一个当前有效目标和一个当前事件范围。

### 2. 何时拆分

拆分依据是可分割的语义所有权，而不是单纯减少 token：

- 有两个及以上可独立排序的事件或因果步骤时，可以按事件边界拆分；
- 只有一个不可再分的事件时，不得伪造两个子任务，应改为同范围重写或续写；
- 正常结束但篇幅不足时，先检查事件和出口状态是否完整；完整则允许作为偏短候选交给父级平衡，不完整且可语义拆分时才拆分；
- 输出上限导致不完整时，先在同一路由增加可用输出空间，再按语义所有权拆分；
- 网络中断只进行同内容同范围重试，不改变任务边界。

### 3. 动态目标

第一个子任务完成后，第二个子任务的目标根据父级剩余目标、尚未完成事件和最低可用场景空间重新计算，不固定按 50/50 分配。

子任务略微超出目标，但事件完整、没有越界且父级仍有足够剩余空间时，可以接受并缩小后续目标。若它侵占兄弟任务事件、导致兄弟任务无法完成或使父级必然超出允许范围，只重写该子任务，不机械截取正文。

最大输出 token 继续用于避免供应商截断，不作为强迫正文变短的手段。目标控制通过无冲突提示、事件所有权、动态剩余量和验证完成。

### 4. 逐级验证

每个正常终止状态，包括 `stop`、`end_turn`、`completed` 和输出上限完成，都必须进入同一验证入口。

叶子任务检查：

- 当前事件是否完整且没有写入兄弟事件；
- 入口状态是否承接父级或上一兄弟任务；
- 出口状态是否满足拆分清单；
- 正文是否存在乱码、写作说明、异常重复或明确视角漂移；
- 实际篇幅是否为父级留下足够完成空间。

合并节点检查：

- 所有子事件恰好覆盖一次；
- 事件顺序、因果顺序和时间顺序正确；
- 人物位置、动作、关系和知情状态连续；
- 兄弟任务之间没有场景重写、重复铺垫或突然跳转；
- 合并篇幅在父级允许范围内，或有明确、可验证的动态平衡记录。

完整写作段检查：

- 覆盖本段全部正式事件；
- 达到原定段首和段末状态；
- 不提前消费后续写作段事件；
- 与上一已接受写作段连续；
- 通过项目适用的正文完整性和质量规则。

整篇正文检查：

- 正式大纲事件全部且只覆盖一次；
- 因果链、执行索引和 StoryState 一致；
- 人物、时间线、地点、关系、知情状态连续；
- 伏笔、承诺、显式问题和结局得到正确兑现；
- 开头承诺、高潮和确认结局未因拆分而改变；
- 全篇篇幅和节奏没有因局部拆分失衡。

只有整段和整篇级验证通过，正文才可进入精修、终审和候选稿提交流程。

## 三、超过 token 上限时的全覆盖核对

完整性核对不得因上下文不足降级为抽查。执行顺序如下：

1. 本地对全文执行哈希、事件覆盖、顺序、重复、乱码、篇幅和状态交接检查。
2. 若模型可在安全上下文内读取全文，执行一次完整核对。
3. 若预计输入、权威资料、预期输出和该路由历史推理消耗接近安全边界，按场景和段落建立重叠窗口。
4. 每个窗口接收全篇骨架、适用事件、入口状态、出口要求、结局约束和相邻重叠正文，只返回结构化检查证据，不改写正文。
5. 按时间和因果顺序汇总所有窗口证据，核对跨窗口人物状态、关系、时间线、伏笔和结局。
6. 汇总仍过长时，按幕、章节或因果阶段继续分层归并，但保留稳定事件 ID、问题 ID、状态变化和原文范围。
7. 发现远距离冲突时，携带相关权威资料直接回看对应原文窗口，不能只依赖压缩摘要定案。

每个窗口必须绑定稿件哈希、字符范围和覆盖记录。窗口遗漏、重叠映射不明、汇总截断或全局裁决未完成时，保留已验证证据并停止后续流程。配置了更大上下文的备用模型时可以使用备用模型；所有路由仍无法完成时不得放行。

## 四、恢复、检查点与兼容性

- 已验证叶子任务可写入内部检查点，但在父级通过前不得成为正文权威。
- 失败后只重做无效子树；复用检查点时必须重新核对权威哈希、目标、事件范围、上一兄弟出口和正文哈希。
- 旧版完整段检查点继续可读；缺少新拆分清单的旧版内部子任务不跨运行复用。
- 当前项目文件、模型绑定、Skill、运行记录、StoryState 和正式稿保持不变。
- 新字段写入现有 JSON 检查点并带版本号，不要求破坏性数据库迁移。
- 非中文项目不使用汉字数量作为唯一拆分依据。

## 五、运行事件

运行记录必须显示：

- 父级目标、子级当前目标、允许范围和实际长度；
- 拆分原因、深度、事件范围和剩余事件；
- 当前失败属于输入上下文、输出上限、网络、正常但不完整、事件越界还是合并失败；
- 已保留的有效检查点和将要重做的最小子树；
- 整段验证和整篇验证是否完成。

“模型返回完成”只表示供应商调用结束，不得表示正文任务已经验收。

## 六、项目级强制约束

在 `AGENTS.md` 增加“生成子任务完整性门禁”：

- 任何新增或修改的拆分、重试、续写、压缩或恢复流程都必须重新生成当前任务契约，禁止继承冲突的旧目标和旧范围；
- 正常结束与输出受限必须经过同一产物验证；
- 子任务、合并节点、整段和整篇必须逐级验证；
- token 不足只能改变核对拓扑，不能降低全篇叙事完整性要求；
- 不完整、歧义或过期权威不得进入下游生成；
- 新拆分边界必须有旧目标残留、递归拆分、正常结束但超长、子任务失败、合并失败和全篇逻辑门禁的回归测试。

## 七、测试与验收

### AI 复检

- 已解决问题从活动清单和数量中移除，并进入历史记录；
- 部分解决、待确认和未解决问题保留并重新排序；
- 新问题进入活动清单；
- 旧问题遗漏、重复对账、结果截断、模型失败和稿件哈希变化均不覆盖旧检查点；
- 活动数量、页面展示、默认修复选择和发布阻断使用同一集合；
- 旧版状态和旧检查点保持可读。

### 自动拆分

- 递归子任务提示只包含当前目标，不包含父级冲突目标；
- 正常结束但过长的叶子任务立即被识别；
- 第一个子任务实际长度会调整第二个子任务目标；
- 单一不可分事件不会被机械拆成两个任务；
- 子任务事件不重不漏、顺序正确、入口出口连续；
- 子任务都通过但父级合并失败时不得提交；
- 完整段通过但整篇因果或状态失败时不得进入精修；
- `stop`、`end_turn`、输出上限、网络中断和未知供应商上限分别覆盖；
- 乱码和明显正文损坏被阻断；
- 失败后保留上游有效段和已验证子任务，恢复时只复用哈希一致的产物。

### 完成标准

- 聚焦回归测试通过；
- 完整测试套件通过；
- 文档说明新的问题刷新、拆分、token 核对和失败保护行为；
- 不调用付费模型；
- 不修改任何现有正式稿或用户项目资料。
